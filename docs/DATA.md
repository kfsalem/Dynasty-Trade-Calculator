# The build-time data pipeline

Everything under `public/data/` is generated by `npm run ingest` from
[nflverse-data](https://github.com/nflverse/nflverse-data). This document is why
that is a build step rather than a fetch.

## Why the app cannot fetch this itself

Two independent blockers, verified against live endpoints on 2026-07-30.

**No CORS.** nflverse publishes as GitHub *release assets*, which redirect to
`release-assets.githubusercontent.com`. That host sends no
`Access-Control-Allow-Origin` header, so a browser fetch from
`kfsalem.github.io` is blocked outright. This is specific to release assets —
`raw.githubusercontent.com`, which `src/values/dynastyprocess.ts` uses today,
does send `Access-Control-Allow-Origin: *`.

**Size.** The depth chart file is 53 MB for 2025 and 37 MB for 2026.

| source file | size | reduced to |
|---|---|---|
| `snap_counts_2025.csv` | 2.4 MB | 106 KB |
| `stats_player_week_2025.csv` | 8.5 MB | 208 KB |
| `depth_charts_2026.csv` | 37 MB | 32 KB |
| `db_playerids.csv` (crosswalk) | 2.6 MB | not shipped |

Node enforces no CORS and CI does not pay for the bandwidth, so both problems
disappear by moving the fetch to build time. The app stays a zero-backend static
site.

The depth chart is 53 MB because of *history*, not depth: nflverse appends a
fresh full-league chart every few hours and never prunes, so the 2025 file holds
132 snapshots of the same ~3,000 rows. Keeping only the newest is the entire
reduction.

## What ships

Four files, 346 KB total against a 1 MB budget enforced by the ingest.

| file | contents |
|---|---|
| `snaps.json` | Offensive snaps and snap share, per player-week |
| `opportunity.json` | Targets, target share, air yards share, WOPR, carries, receptions, PPR points, per player-week |
| `depth.json` | Current depth chart position and rank, one row per player |
| `index.json` | What shipped and how fresh it is |

Shapes are declared in `src/data/types.ts`, imported by both the ingest and the
app so the two cannot drift.

Weekly rows are number tuples rather than objects, with the column order
published in the file as `columns`. Repeating eight keys on every player-week
costs roughly half the budget for nothing.

Everything is **keyed by Sleeper id**. Each nflverse dataset keys on a different
id and none of them is Sleeper's — snap counts use `pfr_player_id`, weekly stats
use gsis `player_id`, depth charts use `gsis_id` and `espn_id` — so the
[DynastyProcess crosswalk](https://github.com/dynastyprocess/data) resolves them
here, once, and the client never downloads 2.6 MB to look up ids we already knew.

## Seasons resolve per dataset

The datasets do not advance together. On 2026-07-30 `depth_charts_2026.csv` was
live and being rewritten hourly while `snap_counts_2026.csv` and
`stats_player_week_2026.csv` were still 404 — offseason depth charts exist,
offseason snaps do not. So each dataset probes for its own newest published
season. Assuming one season across all three either 404s the whole build in July
or pins depth charts a year stale in September.

This is why `throughWeek` is per file, and why `depth.json` carries `asOf`
instead: a chart is a snapshot, not a season.

## Failure policy

The two failure modes are deliberately different, because confusing them is how
a data pipeline rots quietly.

**A network failure must not break a deploy.** nflverse being down does not make
the committed copy of `public/data` wrong, only older. The ingest warns, keeps
the committed copy, marks it `fresh: false` in `index.json`, and exits 0. The
build ships. The one case that does fail is an outage with no committed copy at
all, because then there is genuinely nothing to ship.

**Schema drift must break the build.** A renamed column, a file with no rows, or
a reduction that collapses to almost nothing all fail loudly with a message
naming the dataset and the columns involved. This matters more than it sounds:
a source that parses into an empty result looks exactly like an offseason, and
nobody would notice for weeks.

Both paths are covered in `scripts/ingest/*.test.ts`.

## Refresh

`.github/workflows/refresh-data.yml` runs the ingest weekly on Tuesdays from
September through February, and commits the result. Tuesday because nflverse
finishes reprocessing Monday night's game some time Tuesday morning, which is
the first moment the previous week is complete.

Committing the refreshed data is the point — it is what keeps the fallback copy
current. Without it the fallback would only ever be as fresh as the last code
push.

A push made with `GITHUB_TOKEN` deliberately does not trigger other workflows,
so the refresh job dispatches `deploy.yml` explicitly at the end.

Run it by hand any time with `npm run ingest`, or via **workflow_dispatch** in
the offseason.

## Known limits

- **Match rates are reported, not enforced.** The run prints per-position match
  rates and names the unmatched. A threshold that fails the build is R2.
- Match rates as of 2026-07-30: snaps 97.0%, opportunity 98.0%, depth 83.0%.
  Depth is lower because an offseason 90-man chart is full of camp bodies who
  are in no dynasty player database. A threshold has to survive that, which is
  the main reason it is not set yet.
- Only offensive skill positions (QB/RB/FB/WR/TE) are ingested. K and DEF have
  no published values to attach activity to — see R10.
- The reduction keeps every regular-season week rather than pre-aggregating.
  Season-to-date versus last-four is a windowing decision, and baking one window
  in here would mean re-running the ingest to change it.
